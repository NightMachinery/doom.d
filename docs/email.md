# Email: notmuch, mbsync and msmtp

Mail is read in Emacs with notmuch, kept in a local Maildir by mbsync, and sent
by msmtp. Everything is in this repository except the account's identity and
its password: the identity lives in a private file, and the password in the
macOS login Keychain. Doom's `:email` module is not used.

## The three layers

- **Reader**: notmuch.el, the Emacs client for notmuch. notmuch indexes the
  Maildir into a Xapian database and answers searches from it, so reading and
  searching work offline and are instant. It has no long-running server, so
  both Emacs processes (the terminal daemon and the GUI) can use it at once.
- **Syncer**: mbsync (the isync package). It keeps `~/Mail/<account>/` and the
  IMAP server in step, in both directions: new mail, flags, and files that
  moved between folders.
- **Sender**: msmtp. Emacs hands it the finished message, and msmtp picks the
  account from the From header.

A **sync** is one run of `email/bin/night-mail-sync`. It holds a lock (so only
one sync runs at a time, whoever started it) and runs `notmuch new`, whose two
hooks do the real work:

1. `email/notmuch-hooks/pre-new` moves files between folders according to
   their tags, then runs `mbsync -a`.
2. notmuch indexes whatever changed.
3. `email/notmuch-hooks/post-new` turns what the server did into tags, then
   dumps all tags as a backup.

A LaunchAgent (`com.user.night-mail-sync`) runs a sync every five minutes and
at login, whether or not Emacs is open. In Emacs, `night/mail-sync` runs one
on demand, asynchronously. On macOS it requests a fresh run through that
LaunchAgent, so credential lookup uses the graphical login session regardless
of how Emacs was started.

New unread inbox arrivals also produce configurable desktop notifications from
`Night Mail.app`, with its own envelope icon and macOS notification settings.
See "Desktop notifications" below.

## Where things live

In this repository, under `email/`:

- `templates/`: the configs for mbsync, msmtp, notmuch and the LaunchAgent,
  with `@NIGHT_MAIL_*@` placeholders where the identity goes.
- `bin/night-mail-render`: fills the templates in from the identity file.
- `bin/night-mail-sync`: one sync, as described above.
- `bin/night-mail-request`: asks the installed LaunchAgent for a fresh run and
  waits for its matching completion status, forwarding that run's log to Emacs.
- `bin/night-mail-lib.bash`: shared by the sync script and the hooks.
- `notmuch-hooks/pre-new`, `notmuch-hooks/post-new`: the tag and folder rules.
- `install-night-mail.zsh`: renders the configs and installs the LaunchAgent;
  `--check` reports its state, `--uninstall` removes it.
- `identity.env.example`: the keys the identity file must set.

Emacs: `autoload/night-email.el` (the client), the notmuch pin in
`packages.el`, and the "e" capture template in `autoload/org/night-protocol.el`.

Private, outside the repository:

- `~/.config/night-mail/identity.env` (mode 600): the account's short name,
  display name, address and aliases, IMAP username and host. Nothing else
  reads it except `night-mail-render`.
- The login Keychain: one internet password, server = the host, account = the
  IMAP username.

Generated by `night-mail-render`, each carrying a "Generated by
night-mail-render" marker line. They sit where each tool looks by default, so
plain `notmuch`, `mbsync` and `msmtp` work from a shell:

- `~/.config/isyncrc`
- `~/.config/msmtp/config`
- `~/.config/notmuch/default/config`
- `~/Library/LaunchAgents/com.user.night-mail-sync.plist`

Edit the templates, never these. `night-mail-render` refuses to overwrite a
file that lacks the marker, so it cannot clobber a config written by hand.

State: mail in `~/Mail/<account>/`, the notmuch database in `~/Mail/.notmuch/`,
tag dumps in `~/.local/share/night-mail/tag-dumps/`, the lock and the msmtp
log in `~/.local/state/night-mail/`, the sync log in
`~/logs/night-mail-sync.log`.

## Setting up a machine

1. `brew install notmuch isync msmtp flock`
2. Copy `email/identity.env.example` to `~/.config/night-mail/identity.env`,
   fill it in, and `chmod 600` it.
3. Put the password in the Keychain, typing it at the prompt:

       security add-internet-password -U -a USER -s HOST -l 'mail (night-mail)' -w "$HOME/Library/Keychains/login.keychain-db"

   Because `security` itself creates the item, it is on the item's access
   list, so mbsync and msmtp (which call `security find-internet-password`)
   read it without a dialog. To script this, feed the password through a
   pseudo-terminal rather than on the command line, where `ps` would show it.
   Wait for each prompt first: `security` flushes pending input when it
   prompts, so text sent early is thrown away and it waits forever.
4. `email/install-night-mail.zsh`. This bootstraps the dedicated notification
   app using the shared builder in `$NIGHTDIR/macos/notification-apps/` (or
   `~/scripts/macos/notification-apps/`), renders the configs, creates the
   Maildir root and starts the LaunchAgent, whose first run downloads the
   mail.
5. `doom sync`, then restart Emacs (or load the new packages by hand).

The first sync on an empty database downloads everything, indexes it, and
tags the INBOX mail `inbox` and the Sent mail `sent`. The mover does nothing
on that run, since there are no tags yet to act on.

## Desktop notifications

`email/install-night-mail.zsh` automatically builds, signs, and registers
`~/Applications/Night Mail.app`. It shares its builder with the zsh Agent Bells
app, but each app has its own icon, permission, and alert style. The first install
requests macOS notification permission and sends a silent setup notification.
Allow Night Mail in System Settings → Notifications. The existing Homebrew
terminal-notifier is untouched. Setup needs Python 3.9+ and Apple's Command Line
Tools. Downloads are cached and checksum-pinned; reruns reuse current builds and
preserve your previous app if rebuilding fails.

Settings live in `~/.config/night-mail/notifications.json` (or under
`$XDG_CONFIG_HOME`). Setup creates this file with safe defaults only if absent;
edits apply on the next sync without restarting Emacs or launchd. The environment
override `NIGHT_MAIL_NOTIFY_CONFIG` selects another file for a particular run.

The initial configuration is:

```json
{
  "defaults": {
    "enabled": true,
    "show_details": true,
    "sound": null,
    "bypass_dnd": false,
    "max_individual": 3
  },
  "groups": [
    {"name": "Other mail"}
  ]
}
```

Groups are ordered: the first matching group wins, and omitted settings inherit
`defaults`. Each matching field (`from`, `subject`) is a case-insensitive Python
regex; when both are specified, both must match. Headers are decoded first;
`from` includes the display name and address. Bodies are not searched. The final
group must omit `match`, making it an unconditional catch-all. Names must be
unique. For example, replace the groups above with:

```json
[
  {
    "name": "Digests",
    "match": {"from": "robot@", "subject": "digest"},
    "enabled": false
  },
  {
    "name": "Urgent",
    "match": {"subject": "\\burgent\\b"},
    "sound": "Glass",
    "bypass_dnd": true
  },
  {"name": "Other mail"}
]
```

This explicitly opts the Urgent group into DND bypass. The shipped configuration
has no bypass group: all mail respects DND and is silent by default. Optional
bypass uses terminal-notifier 2's private macOS API and is best effort; newer
terminal-notifier versions ignore that option. macOS Focus allowlists and system
notification settings can also affect delivery.

Each group's `max_individual` (1 to 20, default 3) limits individual sender/subject
alerts per sync. Larger batches produce one summary with up to that many
previews. `show_details: false` always produces a count-only summary, keeping
sender and subject off screen. `sound` is a macOS sound name, `"default"`, or
`null` for silence. Set `defaults.enabled` to false to disable all groups that
do not explicitly override it.

Alerts cover newly indexed unread messages in an inbox, excluding spam, deleted
mail, and drafts. Initial mailbox imports stay silent. Existing unread mail,
folder moves, duplicate message files, and flag changes do not repeatedly alert.
`pre-new` compares the database UUID with the previous baseline. The first sync
after installation or a database rebuild stays silent; an initialized empty
mailbox can notify on its first later arrival.

`post-new` applies folder tags, runs `email/bin/night-mail-notify` while the `new`
tag still identifies arrivals, then clears `new` and backs up tags. Notifications
are best effort: malformed configuration or an unavailable helper is logged,
mail sync continues, and failed/disabled alerts are not retried later. Rule group
names control policy and batching, not terminal-notifier's replacement group:
individual alerts do not replace each other.

`email/install-night-mail.zsh --check` checks the app, signature, authorization,
and rule file. Run `python3 tests/night-mail-notify-test.py` for hermetic policy
tests and real notmuch hook tests against a synthetic mailbox and fake notifier.
Email uninstall removes only the LaunchAgent, preserving apps and settings.

## Using it

- `SPC o m` opens the inbox (`night/notmuch-inbox`), `SPC o M` the notmuch
  hello screen. The saved searches: inbox, unread, flagged, todo, waiting,
  sent, drafts, all, trash.
- evil-collection supplies the keys: `RET` opens, `a` archives, `d` toggles
  `deleted`, `!` toggles unread, `=` toggles flagged, `+`/`-` add or remove a
  tag, `cc` composes, `cr`/`cR` reply to the sender or to all, `s` searches.
- `notmuch-jump-search` jumps to a saved search by the search's `:key`: `i`
  inbox, `u` unread, `f` flagged, `t` todo, `w` waiting, `s` sent, `d`
  drafts, `a` all, `D` trash. In normal state it is `J` (evil-collection),
  since `j` moves down a line; in insert or emacs state, e.g. while the
  hello screen's search field has focus, it is notmuch's own `j`. So `J i`
  or `j i` opens the inbox. We add no `g` keys for these, because `gs` (avy
  and link-hint) and `gt` (next tab) are worth keeping.
- `K` opens a tag menu (`notmuch-tagging-keys`): archive, delete, flag,
  unflag, read, unread, todo, done, waiting, no longer waiting. evil-collection
  binds it, but Doom keeps `K` for `+lookup/documentation`, so
  night-email.el binds it again.
- `gR`, the hello screen's `G`, and localleader `u` all run `night/mail-sync`.
  `notmuch-poll` is advised to do so, because on its own it blocks Emacs for
  the whole sync. The log goes to the buffer ` *night-mail-sync*`.
  Fetch failures report `fetch FAILED` even when local indexing succeeds; that
  partial success still refreshes the mail views.
- Localleader `c` composes, localleader `/` searches with `consult-notmuch`.
- HTML mail is shown as Org; see "HTML mail" below. In a message,
  localleader `h` switches HTML between Org and shr, `l` toggles links
  between `[[url][text]]` and just the text, and `o` opens the message's
  HTML as an Org buffer.
- Composing is plain text. In a message, localleader `h` (`org-mime-htmlize`)
  turns Org markup in the body into an HTML part, and localleader `e` edits
  the body in an Org buffer.
- `org-store-link` on a message gives a `notmuch:id:` link (from
  `ol-notmuch`). The capture template "e" files a TODO with the subject,
  sender and link under "Email" in the notes inbox.
- Sent mail is filed in `<account>/Sent` tagged `sent`, drafts in
  `<account>/Drafts`. mbsync uploads both to the server.

## HTML mail

A text/html part is converted by pandoc and shown as fontified Org, in place
of shr, the browser-like renderer notmuch uses by default.
`night/h-notmuch-show-html` advises `notmuch-show-insert-part-text/html`:

- pandoc runs with `email/html-to-org.lua`, a filter for what HTML mail is
  made of. Tables used for page layout (anything but a table of at least two
  rows and columns of one-paragraph cells) are replaced by their contents.
  Images become their alt text, so tracking pixels vanish, and a link left
  empty by that is dropped. Divs, spans and raw HTML are unwrapped or
  dropped, and ids and styles are cleared so no `:PROPERTIES:` drawers appear.
- The Org text is fontified in a temporary Org buffer. Links stay literal,
  `[[url][text]]`, and each is a button from its URL on: `RET` opens
  `http(s)` and `mailto` links in the browser or composer, and only shows
  any other kind. Mail is untrusted, so an `elisp:` or `shell:` link must
  never run. The button starts at the URL, not the brackets, so that
  link-hint (`gl`) gives one hint per link rather than one for the button
  and one for the bare URL. Faces are copied to `font-lock-face`, because
  font-lock in the notmuch buffer strips `face`.
- The parts of a link Org would hide carry `invisible org-link`.
  Localleader `l` (`night/notmuch-toggle-link-display`, also what
  `org-toggle-link-display` is remapped to in a message) toggles between
  literal links and Org's descriptive display. The choice,
  `night/notmuch-link-display`, holds for every message buffer, open or
  later, and savehist keeps it across sessions. While links are
  descriptive, moving point onto one shows its URL in the echo area
  (`night/h-notmuch-echo-link-url`, a buffer-local `post-command-hook`). Org's own command cannot do
  it here: it works by refontifying, and a notmuch buffer has no Org
  font-lock.
- If pandoc is missing or fails, or the part is over
  `night/notmuch-html-org-max-size`, shr renders it as before.
- Of a multipart/alternative message, the HTML is shown rather than the plain
  text (`notmuch-multipart/alternative-discouraged` is `("text/plain")`). The
  plain part is still a button away.

Localleader `h` (`night/notmuch-toggle-html-renderer`) switches between Org
and shr, e.g. for a message whose images matter. Localleader `o`
(`night/notmuch-show-html-in-org`) opens the message's HTML as a read-only
Org buffer, for folding, `org-store-link` or copying into notes. That buffer
sets `night/mail-buffer-p`, so the LLM policy refuses it like any mail view.

On this mailbox's 51 HTML parts the conversion took 50 to 150 ms each.

## Tags and folders

notmuch tags live only in its database. The server knows folders, plus five
standard flags that mbsync does carry: `unread`, `flagged`, `replied`,
`draft` and `passed` round-trip as IMAP flags (`maildir.synchronize_flags`).
Any other tag (`todo`, `waiting`, a project name) is private to this machine;
mbsync does not sync IMAP keywords at all. Such a tag is still durable: it is
keyed on the Message-ID, so it survives renames, moves between folders and
mbsync's flag changes. See "Backing up tags" for the one way to lose it.

Two tags mean "where it is", and are turned into folder moves so that the
phone and webmail agree with Emacs. pre-new moves, per account:

- `deleted` in INBOX, Sent or Archive: to Trash.
- `deleted` in Drafts: the file is removed. notmuch tags a draft `deleted`
  when it is sent or resumed.
- INBOX without `inbox` (archived): to Archive. mbsync creates the server's
  `Archive` folder the first time.
- Archive with `inbox` (unarchived): to INBOX.
- Trash without `deleted` (undeleted): to Sent if it is sent mail no longer in
  the inbox, otherwise to INBOX.

A moved file drops the `,U=<uid>` part of its name (mbsync would otherwise see
a duplicate UID) and keeps its `:2,FLAGS` suffix (the read and flagged state).
mbsync then uploads the new copy and expunges the old one (`Expunge Both`),
keeping the arrival date (`CopyArrivalDate yes`).

post-new does the reverse, for what the server did, per account:

- In Trash but not `deleted`: tagged `deleted`, and removed from the inbox.
  Deleted on the phone.
- **Changed this run**, in INBOX, still `deleted`: untagged, back in the inbox.
  Restored from Trash on the phone.
- Changed this run, in INBOX, not in the inbox: tagged `inbox`. Moved back to
  INBOX on the phone, or the server's copy of mail you sent yourself.
- New in INBOX: `inbox`. New in Sent: `sent`.
- Tagged `inbox` but not in INBOX: `inbox` removed. Archived on the phone.

With several accounts, the final rule checks all inbox folders together. The
message-wide `inbox` tag is kept while any copy remains in any account's inbox.

"Changed this run" means a file of the message appeared, vanished or was
renamed during this sync. pre-new records the database revision before it
starts, and post-new asks for `lastmod:<revision>..`. Without it, a message
restored on the phone would still carry `deleted` from before, and the next
sync would move it straight back to Trash.

The cost of that rule: a tag you change in Emacs *during* the few seconds a
sync spends indexing can be overridden by the server's view, e.g. an archive
undone. Nothing is ever lost that way; archive again.

post-new never adds `unread`. notmuch derives it from the S flag, and adding
it again would clear S, so mail read on the phone would come back unread on
the server.

**Safety limit.** When a sync would move more than `NIGHT_MAIL_MOVE_LIMIT`
files (default 100), pre-new moves nothing and logs why: that many moves at
once means the tags are wrong, for example after a `notmuch new --no-hooks`
left new mail without its `inbox` tag. (Mail still tagged `new` is never
archived, for the same reason.) To do a genuine bulk move, run one sync with
the limit lifted:

    NIGHT_MAIL_MOVE_LIMIT=0 ~/doom.d/email/bin/night-mail-sync --wait 600

Always sync every folder before indexing (`mbsync -a`, which pre-new does).
Indexing after syncing only INBOX would see a message the phone moved out of
INBOX as vanished, and drop its tags.

## Backing up tags

Tags are the only thing in the database that the mail files cannot rebuild.
Rebuilding or deleting the database, or moving to a new machine, loses them
unless they are restored. post-new writes `notmuch dump --gzip` after every
sync into `~/.local/share/night-mail/tag-dumps/tags-<weekday>.gz`, seven
rotating files. To restore one:

    notmuch restore --accumulate --input=~/.local/share/night-mail/tag-dumps/tags-3.gz

`--accumulate` adds the dump's tags to the current ones; without it, restore
replaces them. For history or a second machine, `notmuch git` (shipped with
Homebrew's notmuch) keeps tags in a git repository. Keep any such repository
private: tag names can be revealing.

## Concurrency

Every sync goes through `night-mail-sync`, which takes an exclusive `flock` on
`~/.local/state/night-mail/sync.lock`. The LaunchAgent does not wait: a tick
that finds a sync running exits 75 and leaves the work to the next one.
`night/mail-sync` in Emacs waits up to `night/mail-sync-wait` seconds (600).
A bare `notmuch new` from a shell takes the lock in pre-new itself.

On macOS, Emacs uses `night-mail-sync --request --wait 600`. This serializes
requests, assigns a unique token, and starts the existing LaunchAgent without
killing a running job. If an older sync is already running, its completion does
not satisfy the request: the requester waits for a run that started after the
request. The worker's `--launchd` mode publishes the matching token and exit
status atomically. Timeouts leave any active worker running safely.

`pre-new` records mbsync's status in `~/.local/state/night-mail/fetch-status`.
The main wrapper returns 69 when fetching failed but indexing succeeded, 75
when the lock was busy, or notmuch's failure status when indexing failed. It
clears stale fetch status before each run. Direct `notmuch new` still indexes
local mail after a fetch failure; use the wrapper for the combined fetch/index
exit status. The request/result files in that directory contain tokens and
status codes, not credentials.

Regression checks: `python3 tests/night-mail-request-test.py` covers request
matching, an already-running sync, launch races, unavailable services, and safe
timeouts. `emacs -Q --batch -l tests/night-email-sync-test.el` covers command
routing and partial-failure reporting. The real-notmuch synthetic-mailbox suite
also verifies indexing and completion acknowledgements after fetch failure.

notmuch.el opens the database per command and waits for the write lock
rather than failing, so tagging from either Emacs during a sync just pauses
briefly. Tested with both servers tagging while a sync ran.

## Upgrading notmuch

notmuch.el must match the notmuch CLI. It is built from the pinned upstream
tag by Doom, not taken from Homebrew, whose `.elc` files are compiled by
Homebrew's newer Emacs. After `brew upgrade notmuch`:

1. Find the new tag's commit:
   `git ls-remote https://git.notmuchmail.org/git/notmuch 'refs/tags/0.41^{}'`
2. Update the `:pin` in `packages.el` and `night/notmuch-pinned-version` in
   `autoload/night-email.el`.
3. `doom sync`, then restart Emacs.

When notmuch loads, `night/h-notmuch-version-check` warns if the CLI and the
pin differ, and `install-night-mail.zsh --check` reports the same.

## Privacy

- The password is only in the Keychain. The configs name a
  `security find-internet-password` command, never the password.
- The identity file is private, and the repository never names the account:
  Emacs reads the name and addresses from the rendered notmuch config, and
  finds the account's folder by looking for an INBOX under the mail root.
- `night/llm-path-policy` (see [llm-context.md](llm-context.md)) refuses to
  send notmuch buffers, the Maildir, the identity file and `~/.*_pass` files to
  a model, and asks first in a message being written, since a reply quotes
  its thread.

## Troubleshooting

- **Sync log**: `~/logs/night-mail-sync.log` for the LaunchAgent, the buffer
  ` *night-mail-sync*` for Emacs. Moves are logged one per line. A quiet log
  means nothing moved and nothing failed.
- **Password entry not found**: mail tools explicitly search
  `~/Library/Keychains/login.keychain-db`. A lookup without a Keychain path
  can fail even when the entry exists there, if the default search list
  omits it. Re-render older configs with `email/bin/night-mail-render`.
- **Fetch failures despite “done”**: the pre-new hook logs mbsync failures
  but allows indexing to finish. The wrapper now returns 69 for this partial
  success, and Emacs reports `fetch FAILED`. Check the sync log for
  `mbsync failed`; successful local indexing alone does not mean mail was fetched.
- **GUI-only `PassCmd exited with status 36`**: a graphical Emacs window does
  not guarantee its children belong to a graphical macOS security session.
  Processes started through a detached multiplexer can lack Keychain access
  even when the same lookup works in a terminal daemon. Emacs sync requests go
  through the Aqua LaunchAgent to use the correct login context. Reinstall with
  `email/install-night-mail.zsh` after updating the plist, then reload
  `autoload/night-email.el` in both servers. Changing `SECURITYSESSIONID` or
  the subprocess's PTY setting does not change its actual security session.
- **Job state**: `email/install-night-mail.zsh --check`.
- **mbsync**: `mbsync -l <account>` lists the server's folders. The server's
  personal namespace is `INBOX.`, which mbsync applies itself
  (`UseNamespace`), so the far side's `Sent` is `INBOX.Sent`.
  `AuthMechs LOGIN` avoids a known problem with macOS's SASL library.
- **msmtp**: `~/.local/state/night-mail/msmtp.log` records every send with
  its SMTP status. Port 465 is TLS from the first byte, so `tls_starttls off`.
- **Nothing moved**: look for "refusing to move" in the log (the safety
  limit).
- **The scripts run under macOS's `/bin/bash` 3.2.** Two traps met while
  writing them: a failing `command grep` inside an `if` still trips `set -e`
  (so none of the scripts use `-e`), and `${s//pat/"rep"}` keeps the quotes
  literally (so `night-mail-render` substitutes with perl).

## Removing it

`email/install-night-mail.zsh --uninstall` stops and removes the LaunchAgent.
Mail, tags, the generated configs and the Keychain item are left alone;
delete `~/Mail`, the four generated files and the Keychain item by hand if
you mean it.
